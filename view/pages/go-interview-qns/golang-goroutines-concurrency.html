Goroutine Basics

What is a Goroutine?

A goroutine is a lightweight thread managed by the Go runtime. It's not an OS thread - it's much lighter and cheaper to create.

Lightweight

~2KB stack (vs 1-2MB for OS threads)

Cheap

Can run millions concurrently

Managed

Go runtime handles scheduling

package main

import (
    "fmt"
    "time"
)

func main() {
    // Sequential execution
    sayHello("Alice")
    sayHello("Bob")
    // Takes ~2 seconds total
    
    // Concurrent execution with goroutines
    go sayHello("Charlie")  // Runs in separate goroutine
    go sayHello("David")    // Runs in separate goroutine
    
    // Main goroutine continues immediately
    fmt.Println("Main function continues...")
    
    // Wait for goroutines to complete
    time.Sleep(2 * time.Second)
    // Takes ~1 second total (both run concurrently)
}

func sayHello(name string) {
    time.Sleep(1 * time.Second)
    fmt.Printf("Hello, %s!\n", name)
}

// Output (order may vary):
// Hello, Alice!
// Hello, Bob!
// Main function continues...
// Hello, Charlie!
// Hello, David!

⚠️ Important: The main goroutine doesn't wait for other goroutines. If main exits, all goroutines are terminated immediately!

Concurrency vs Parallelism

"Concurrency is about dealing with lots of things at once. Parallelism is about doing lots of things at once." - Rob Pike

🔄 Concurrency

  • • Composition of independently executing tasks
  • • Tasks can run on single core (time-slicing)
  • • About structure and design
  • • Example: Juggling multiple balls

⚡ Parallelism

  • • Simultaneous execution of tasks
  • • Requires multiple cores
  • • About execution
  • • Example: Multiple people juggling
package main

import (
    "fmt"
    "runtime"
    "sync"
)

func main() {
    // Check available CPU cores
    fmt.Println("CPU cores:", runtime.NumCPU())
    
    // Set max CPUs for parallelism (default is NumCPU)
    runtime.GOMAXPROCS(4)  // Use 4 cores
    
    // Concurrent execution (may or may not be parallel)
    var wg sync.WaitGroup
    
    for i := 0; i < 10; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            // CPU-intensive work
            sum := 0
            for j := 0; j < 1000000; j++ {
                sum += j
            }
            fmt.Printf("Goroutine %d done on CPU %d\n", id, runtime.NumCPU())
        }(i)
    }
    
    wg.Wait()
    
    // With 1 CPU: Concurrent but NOT parallel (time-sliced)
    // With 4+ CPUs: Concurrent AND parallel (truly simultaneous)
}

// Key Insight:
// - Concurrency enables parallelism
// - You can have concurrency without parallelism
// - You cannot have parallelism without concurrency

Go Runtime & Scheduler (GMP Model)

The GMP Model

Go uses a sophisticated M:N scheduler that multiplexes M goroutines onto N OS threads.

G - Goroutine

Lightweight execution context with its own stack

M - Machine (OS Thread)

Actual OS thread that executes goroutines

P - Processor

Scheduling context, holds runnable goroutines

How It Works

  • P (Processor): Number of Ps = GOMAXPROCS (default: number of CPU cores)
  • M (Machine): Created on demand, can be more than Ps
  • G (Goroutine): Scheduled onto Ps, executed by Ms
  • Work Stealing: Idle Ps steal goroutines from busy Ps
  • Preemption: Goroutines are preempted at function calls (cooperative scheduling)
package main

import (
    "fmt"
    "runtime"
    "time"
)

func main() {
    // Runtime information
    fmt.Println("GOMAXPROCS:", runtime.GOMAXPROCS(0))
    fmt.Println("NumCPU:", runtime.NumCPU())
    fmt.Println("NumGoroutine:", runtime.NumGoroutine())
    
    // Create many goroutines
    for i := 0; i < 100; i++ {
        go func(id int) {
            time.Sleep(1 * time.Second)
        }(i)
    }
    
    time.Sleep(100 * time.Millisecond)
    fmt.Println("Active goroutines:", runtime.NumGoroutine())
    
    // Force garbage collection
    runtime.GC()
    
    // Get memory stats
    var m runtime.MemStats
    runtime.ReadMemStats(&m)
    fmt.Printf("Alloc = %v MB\n", m.Alloc/1024/1024)
    
    time.Sleep(2 * time.Second)
}

// Scheduler Behavior:
// 1. Goroutine created → placed in P's local queue
// 2. M picks goroutine from P's queue
// 3. If goroutine blocks (I/O, channel), M parks it
// 4. M picks next goroutine from queue
// 5. Work stealing if queue empty

💡 Key Insights:

  • • Goroutines are multiplexed onto OS threads (M:N scheduling)
  • • Blocking a goroutine doesn't block the OS thread
  • • Go runtime handles all scheduling automatically
  • • Work stealing ensures efficient CPU utilization

Communication & Synchronization

"Don't communicate by sharing memory; share memory by communicating." - Go Proverb

Synchronization Primitives

Channels (Preferred)

  • • Type-safe communication
  • • Built-in synchronization
  • • Prevents race conditions
  • • Idiomatic Go way

sync Package

  • • Mutex, RWMutex
  • • WaitGroup
  • • Once, Cond
  • • Use when channels don't fit
package main

import (
    "fmt"
    "sync"
    "time"
)

// ============ MUTEX EXAMPLE ============
type SafeCounter struct {
    mu    sync.Mutex
    count int
}

func (c *SafeCounter) Increment() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.count++
}

func (c *SafeCounter) Value() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.count
}

// ============ RWMUTEX EXAMPLE ============
type Cache struct {
    mu   sync.RWMutex
    data map[string]string
}

func (c *Cache) Get(key string) (string, bool) {
    c.mu.RLock()  // Multiple readers allowed
    defer c.mu.RUnlock()
    val, ok := c.data[key]
    return val, ok
}

func (c *Cache) Set(key, value string) {
    c.mu.Lock()  // Exclusive write access
    defer c.mu.Unlock()
    c.data[key] = value
}

// ============ WAITGROUP EXAMPLE ============
func main() {
    // Mutex example
    counter := &SafeCounter{}
    var wg sync.WaitGroup
    
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            counter.Increment()
        }()
    }
    
    wg.Wait()
    fmt.Println("Counter:", counter.Value())  // Always 1000
    
    // RWMutex example
    cache := &Cache{data: make(map[string]string)}
    
    // Multiple concurrent reads
    for i := 0; i < 10; i++ {
        go func(id int) {
            cache.Get("key")  // No blocking between readers
        }(i)
    }
    
    // Single write blocks all
    go cache.Set("key", "value")
    
    time.Sleep(100 * time.Millisecond)
}

// ============ SYNC.ONCE EXAMPLE ============
var (
    instance *Singleton
    once     sync.Once
)

type Singleton struct {
    data string
}

func GetInstance() *Singleton {
    once.Do(func() {
        instance = &Singleton{data: "initialized"}
    })
    return instance
}

// once.Do ensures initialization happens exactly once
// even with concurrent calls

💡 When to Use What:

  • • Channels: Passing data between goroutines, signaling, coordination
  • • Mutex: Protecting shared state, simple locks
  • • RWMutex: Read-heavy workloads (caches, configs)
  • • WaitGroup: Waiting for multiple goroutines to complete
  • • Once: One-time initialization (singletons, configs)

Race Conditions & Detection

A race condition occurs when multiple goroutines access shared data concurrently, and at least one modifies it.

package main

import (
    "fmt"
    "sync"
)

// ============ RACE CONDITION (BAD) ============
func raceConditionExample() {
    counter := 0
    var wg sync.WaitGroup
    
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            counter++  // ❌ RACE! Multiple goroutines modifying counter
        }()
    }
    
    wg.Wait()
    fmt.Println(counter)  // Unpredictable! Could be < 1000
}

// ============ FIXED WITH MUTEX ============
func fixedWithMutex() {
    counter := 0
    var mu sync.Mutex
    var wg sync.WaitGroup
    
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            mu.Lock()
            counter++  // ✅ Safe
            mu.Unlock()
        }()
    }
    
    wg.Wait()
    fmt.Println(counter)  // Always 1000
}

// ============ FIXED WITH CHANNEL ============
func fixedWithChannel() {
    results := make(chan int, 1000)
    
    for i := 0; i < 1000; i++ {
        go func(val int) {
            results <- val  // ✅ Safe - channels are thread-safe
        }(1)
    }
    
    counter := 0
    for i := 0; i < 1000; i++ {
        counter += <-results
    }
    
    fmt.Println(counter)  // Always 1000
}

// ============ ATOMIC OPERATIONS ============
import "sync/atomic"

func fixedWithAtomic() {
    var counter int64
    var wg sync.WaitGroup
    
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            atomic.AddInt64(&counter, 1)  // ✅ Atomic operation
        }()
    }
    
    wg.Wait()
    fmt.Println(atomic.LoadInt64(&counter))  // Always 1000
}

func main() {
    raceConditionExample()
    fixedWithMutex()
    fixedWithChannel()
    fixedWithAtomic()
}

🔍 Race Detector:

go run -race main.go
go test -race ./...
go build -race

The race detector finds data races at runtime. Use it during development and testing!

💡 Prevention Strategies:

  • 1. Channels: Share data by communicating
  • 2. Mutex: Protect shared state with locks
  • 3. Atomic: Use atomic operations for simple counters
  • 4. Immutability: Don't modify shared data
  • 5. Confinement: Keep data local to one goroutine

Common Concurrency Patterns

1. Worker Pool Pattern

package main

import (
    "fmt"
    "sync"
    "time"
)

// Worker Pool: Fixed number of workers processing jobs
func workerPool() {
    jobs := make(chan int, 100)
    results := make(chan int, 100)
    
    // Start workers
    numWorkers := 3
    var wg sync.WaitGroup
    
    for w := 1; w <= numWorkers; w++ {
        wg.Add(1)
        go worker(w, jobs, results, &wg)
    }
    
    // Send jobs
    for j := 1; j <= 9; j++ {
        jobs <- j
    }
    close(jobs)
    
    // Wait for workers to finish
    go func() {
        wg.Wait()
        close(results)
    }()
    
    // Collect results
    for result := range results {
        fmt.Println("Result:", result)
    }
}

func worker(id int, jobs <-chan int, results chan<- int, wg *sync.WaitGroup) {
    defer wg.Done()
    for job := range jobs {
        fmt.Printf("Worker %d processing job %d\n", id, job)
        time.Sleep(time.Second)
        results <- job * 2
    }
}

2. Fan-Out, Fan-In Pattern

// Fan-Out: Multiple goroutines read from same channel
// Fan-In: Multiple channels merged into one

func fanOutFanIn() {
    // Input channel
    input := make(chan int)
    
    // Fan-Out: Start multiple workers
    c1 := worker("A", input)
    c2 := worker("B", input)
    c3 := worker("C", input)
    
    // Fan-In: Merge results
    results := merge(c1, c2, c3)
    
    // Send work
    go func() {
        for i := 0; i < 10; i++ {
            input <- i
        }
        close(input)
    }()
    
    // Collect results
    for result := range results {
        fmt.Println(result)
    }
}

func worker(name string, input <-chan int) <-chan string {
    out := make(chan string)
    go func() {
        defer close(out)
        for n := range input {
            out <- fmt.Sprintf("Worker %s processed %d", name, n)
        }
    }()
    return out
}

func merge(channels ...<-chan string) <-chan string {
    out := make(chan string)
    var wg sync.WaitGroup
    
    for _, c := range channels {
        wg.Add(1)
        go func(ch <-chan string) {
            defer wg.Done()
            for v := range ch {
                out <- v
            }
        }(c)
    }
    
    go func() {
        wg.Wait()
        close(out)
    }()
    
    return out
}

3. Pipeline Pattern

// Pipeline: Chain of stages connected by channels

func pipeline() {
    // Stage 1: Generate numbers
    nums := generate(2, 3, 4, 5)
    
    // Stage 2: Square numbers
    squares := square(nums)
    
    // Stage 3: Filter even numbers
    evens := filter(squares)
    
    // Consume results
    for n := range evens {
        fmt.Println(n)
    }
}

func generate(nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums {
            out <- n
        }
    }()
    return out
}

func square(in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in {
            out <- n * n
        }
    }()
    return out
}

func filter(in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in {
            if n%2 == 0 {
                out <- n
            }
        }
    }()
    return out
}

4. Context for Cancellation

import "context"

func contextPattern() {
    // Create context with timeout
    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    defer cancel()
    
    // Start work
    results := make(chan int)
    go doWork(ctx, results)
    
    // Wait for completion or timeout
    select {
    case result := <-results:
        fmt.Println("Result:", result)
    case <-ctx.Done():
        fmt.Println("Timeout:", ctx.Err())
    }
}

func doWork(ctx context.Context, results chan<- int) {
    for i := 0; i < 10; i++ {
        select {
        case <-ctx.Done():
            // Context cancelled, stop work
            return
        case results <- i:
            time.Sleep(500 * time.Millisecond)
        }
    }
    close(results)
}

Best Practices

✅ DO

  • • Use channels for communication between goroutines
  • • Keep goroutines simple and focused
  • • Always handle goroutine cleanup (use defer, context)
  • • Use buffered channels to prevent blocking when appropriate
  • • Prefer sync.WaitGroup over sleep for synchronization
  • • Use context.Context for cancellation and timeouts
  • • Run race detector during testing
  • • Document goroutine lifecycle and ownership

❌ DON'T

  • • Don't create unbounded goroutines (use worker pools)
  • • Don't share memory without synchronization
  • • Don't use time.Sleep for synchronization
  • • Don't forget to close channels when done sending
  • • Don't close channels from receiver side
  • • Don't send on closed channels (panic!)
  • • Don't ignore goroutine leaks
  • • Don't use goroutines for everything (overhead exists)

Common Mistakes

// ❌ Mistake 1: Goroutine closure capturing loop variable
for i := 0; i < 5; i++ {
    go func() {
        fmt.Println(i)  // ❌ All print 5!
    }()
}

// ✅ Fix: Pass variable as parameter
for i := 0; i < 5; i++ {
    go func(n int) {
        fmt.Println(n)  // ✅ Prints 0,1,2,3,4
    }(i)
}

// ❌ Mistake 2: Goroutine leak (never exits)
func leak() {
    ch := make(chan int)
    go func() {
        val := <-ch  // ❌ Blocks forever if nothing sent
        fmt.Println(val)
    }()
    // Goroutine never exits!
}

// ✅ Fix: Use context or timeout
func noLeak() {
    ch := make(chan int)
    ctx, cancel := context.WithTimeout(context.Background(), 1*time.Second)
    defer cancel()
    
    go func() {
        select {
        case val := <-ch:
            fmt.Println(val)
        case <-ctx.Done():
            return  // ✅ Exits on timeout
        }
    }()
}

// ❌ Mistake 3: Forgetting to wait for goroutines
func noWait() {
    go doWork()
    // main exits immediately, goroutine killed!
}

// ✅ Fix: Use WaitGroup or channel
func withWait() {
    var wg sync.WaitGroup
    wg.Add(1)
    go func() {
        defer wg.Done()
        doWork()
    }()
    wg.Wait()  // ✅ Waits for completion
}

// ❌ Mistake 4: Sending on unbuffered channel without receiver
func deadlock() {
    ch := make(chan int)
    ch <- 1  // ❌ DEADLOCK! No receiver
}

// ✅ Fix: Use goroutine or buffered channel
func noDeadlock() {
    ch := make(chan int, 1)  // Buffered
    ch <- 1  // ✅ Works
    
    // Or use goroutine
    ch2 := make(chan int)
    go func() {
        ch2 <- 1  // ✅ Works
    }()
    <-ch2
}

  • ✓ Goroutines are lightweight, cheap, and managed by Go runtime

  • ✓ Use channels for communication, sync primitives for shared state
  • ✓ Always run race detector during development
  • ✓ Prevent goroutine leaks with proper cleanup and context
  • ✓ Use patterns like worker pools, pipelines, and fan-out/fan-in
  • ✓ "Don't communicate by sharing memory; share memory by communicating"
